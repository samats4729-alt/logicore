# LogiCore: безопасный деплой в Railway

Этот проект разворачивается автоматически после изменения основной ветки GitHub.
Нельзя вливать production-изменения, пока не выполнены пункты ниже.

## Перед merge

1. Открыть Postgres-сервис в Railway.
2. В разделе **Backups** создать ручную резервную копию.
3. Дождаться статуса успешного завершения и записать время копии.
4. Убедиться, что GitHub CI у pull request зелёный.
5. Только после этого выполнить merge в основную ветку.

## Что делает Railway

1. Собирает новый образ приложения.
2. Выполняет `pnpm prisma:deploy` как pre-deploy command (см. `apps/api/railway.json`).
3. Команда обновляет схему по журналу миграций (`prisma migrate deploy`).
   Применяются только миграции, которых ещё нет в таблице `_prisma_migrations`.
   Любая ошибка миграции завершает pre-deploy, и деплой не продолжается —
   прод остаётся на предыдущей версии.
4. Запускает только `node dist/main`. Seed, очистка данных и backfill автоматически не выполняются.
5. Проверяет `GET /monitoring/health`. Ответ считается успешным только при доступной базе.
6. После успешной проверки переключает трафик на новую версию.

## Быстрая проверка после деплоя

- вход в систему;
- открытие списка заявок и одной существующей заявки;
- открытие бухгалтерии, счетов и взаиморасчётов;
- создание PDF существующего счёта или акта;
- поиск казахстанского и международного адреса через 2GIS;
- проверка списка стран, регионов и городов;
- проверка логов Railway на ошибки Prisma, 500 и повторные перезапуски.

## Откат

1. При ошибке приложения в Railway открыть **Deployments** и вернуть предыдущий успешный deployment.
2. Новые поля текущего релиза добавочные, поэтому предыдущая версия приложения может их игнорировать.
3. Если повреждены данные, не исправлять таблицы вручную. В Postgres открыть **Backups**, выбрать созданную перед merge копию и выполнить Restore.
4. После восстановления проверить вход, заявки и бухгалтерские суммы до возобновления работы пользователей.

## Переход на Prisma Migrate (выполнен)

Production-база исторически обновлялась через `prisma db push`, без журнала изменений.
История в `prisma/migrations/` была неполной: все прежние миграции вместе создавали
33 таблицы при 65 моделях в схеме — воспроизвести базу с нуля по ней было нельзя.

Что сделано:

- прежние 19 миграций заменены одной нулевой `0_init`, снятой с актуальной схемы;
- `prisma:deploy` теперь запускает `apps/api/scripts/deploy-db.js`;
- CI применяет миграции к чистой базе и отдельным шагом доказывает, что результат
  совпадает со `schema.prisma` (`prisma migrate diff --exit-code`).

### Первый деплой после перехода

Ручных действий не требуется. `deploy-db.js` сам определяет состояние базы:

- **таблицы есть, журнала нет** (текущее состояние прода) — отмечает `0_init` как уже
  применённую (`migrate resolve`), структуру не меняет, данные не трогает;
- **база пустая** — создаёт структуру миграциями с нуля;
- **журнал уже есть** — обычный `migrate deploy`.

Ветка с отметкой срабатывает один раз: после неё журнал существует всегда.
В логах Railway это видно строкой `[deploy-db] База управлялась через db push`.

Если бы отметки не было, `migrate deploy` остановился бы с ошибкой `P3005`
(«The database schema is not empty») и деплой бы не прошёл — без изменений в базе.

### Дальше

Новые изменения схемы вносятся только миграциями: `pnpm --filter api prisma:migrate`
локально, миграция коммитится вместе с изменением `schema.prisma`. CI не пропустит
изменение схемы без миграции.
