# LogiCore — аудит продукта и план доводки до рабочего состояния

> Источник правды по доводке бухгалтерии, заявок, документов и регистрации.
> Исполнитель (человек или ИИ-агент) берёт задачу, отмечает `[x]`, пишет
> заметку в «Журнал» внизу. Составлен по итогам полного анализа кода.
>
> Дата: 25.07.2026. Смежные документы: `AGENTS.md` (правила работы),
> `DATA_FOUNDATION_PLAN.md` (фундамент данных — выполнен),
> `ACCOUNTING_ROADMAP.md` (стратегия бухгалтерии), `PRODUCTION_DEPLOY.md`.

## Режим работы: продакшен без реальных данных

Подтверждено владельцем 25.07.2026: реальных пользователей и реальных
данных в проде НЕТ, всё тестовое. Это ускоряет работу — используй:

- **Ломающие миграции разрешены.** Можно менять/удалять колонки и таблицы
  без backfill-скриптов, переходных периодов и совместимости со старыми
  данными. Не нужны «двухфазные» переезды.
- **Старые данные не сохранять.** Вопрос «мигрировать ли старые счета»
  закрыт: НЕ мигрировать. Старую модель Invoice после T-01 можно выводить
  из UI сразу, а затем удалять целиком.
- **Базу можно пересоздавать.** Справочники восстанавливаются сидом
  (`prisma:seed`); при сломанной миграции проще пересоздать, чем чинить.
- **Не писать код обратной совместимости** «на случай старых записей» —
  таких записей нет.

Что это НЕ отменяет (дисциплина дешевле, чем расследования):
- миграции по-прежнему через Prisma Migrate (CI проверяет схему);
- tsc + тесты перед коммитом — они ловят ошибки, а не защищают данные;
- безопасность по-прежнему всерьёз: регистрация открыта в интернет,
  тестовость данных не делает дыры безобидными;
- деньги только в Decimal — это про корректность расчётов, не про данные.

Когда появится первый реальный клиент — владелец убирает этот раздел, и
все послабления автоматически перестают действовать.

## Правила для агентов (обязательные)

1. Прочитать `AGENTS.md`. Кратко: проект в проде; перед коммитом
   `npx tsc --noEmit` в `apps/web` (и в `apps/api`, если менялся API);
   `pnpm --filter api test`; никакого `any` в новом коде.
2. Схема БД меняется ТОЛЬКО миграцией: `pnpm --filter api prisma:migrate`,
   миграция коммитится вместе со schema.prisma. CI не пропустит расхождение.
3. Деньги — только `Decimal` (`apps/api/src/common/utils/money.ts`: `D`,
   `sumOf`, `roundMoney`, `toNum`). Наружу (HTTP/PDF) — числа; глобальный
   `DecimalToNumberInterceptor` уже стоит.
4. Одна задача = один коммит = внятное сообщение. Тест обязан падать на
   старом поведении (проверять подменой), а не просто быть зелёным.
5. Ничего не деплоить: пуш в ветку, мерж в `main` делает владелец.

# Находки анализа

## A. Бухгалтерия: главный разрыв — два поколения документов

**Факт.** В API построена полноценная подсистема документов
`apps/api/src/accounting-documents/` (модель `AccountingDocument`:
счёт/акт/акт сверки, строки, жизненный цикл Черновик → Проведён → Отменён,
`POST :id/post`, `POST :id/cancel`, `GET :id/pdf`, снимки реквизитов сторон,
нумерация `AccountingDocumentNumbering`). Это ровно то, чего требует
`ACCOUNTING_ROADMAP.md` («акт не сохраняется как документ», «нет снимка
реквизитов», «нет Черновик→Проведён→Отменён»).

**Но веб к ней НЕ подключён вообще** (проверено: ни одного обращения к
`/accounting-documents` из `apps/web`). Веб живёт на старом поколении:
- счета — старая модель `Invoice` (итог одной суммой, без строк услуг);
- акт работ — HTML-страница `company/accounting/act-of-work/page.tsx`,
  строится из ТЕКУЩЕЙ заявки: изменение заявки задним числом меняет уже
  распечатанный акт;
- акт сверки — `company/accounting/reconciliation-act/page.tsx`, тоже
  live-расчёт без фиксации.

Из-за этого же «правильные» PDF (которые мы привели к бланку Р-1) пользователю
сейчас недоступны — он видит только старые HTML-версии.

## B. Печати и подписи ставятся автоматически (жалоба владельца)

**Факт.** Картинки печати/подписи загружаются в настройках компании
(`company.controller.ts:216-247`, `settings/page.tsx`) и дальше вставляются в
документы БЕЗ вопроса:
- договор — печати ОБЕИХ сторон, если картинки есть
  (`contracts/contract-pdf.service.ts:42-57, 332`);
- доверенность — печать и подпись эмитента
  (`orders/power-of-attorney.service.ts:55-62`).

Проблемы: (1) нет флажка «Подпись и печать» как в 1С — документ без печати
получить нельзя; (2) печать КОНТРАГЕНТА ставится его картинкой без его
действия — юридически это имитация подписания другой стороной.
В новых PDF (`accounting-document-pdf.service.ts`) печатей нет вовсе —
задача добавить их туда уже с опцией.

## C. Регистрация: чужой/несуществующий БИН

**Факт.** `auth.service.ts:348-407`: регистрация создаёт компанию всегда;
угон истории внешней компании по БИН уже закрыт (совпадение только
логируется в AuditLog). Есть eGov-проверка `GET /auth/company-lookup/:bin`
(`auth.controller.ts:149`), но форма регистрации
(`apps/web/src/app/register/page.tsx`) её НЕ вызывает — БИН уходит как ввели.
Поля верификации у Company нет (`isVerified` в схеме — это про Document).

Итог: любой может зарегистрировать компанию с чужим или выдуманным БИН и
работать от её имени (выставлять счета с реквизитами!). Пока клиентов нет —
не горит, но к открытым регистрациям это должно быть закрыто.

## D. Акт сверки: не как в 1С (пожелание владельца)

1С-версия (эталон-скриншот): колонки Дата, №, № заявки/приход,
Маршрут/Комментарий, Водитель, Счёт, Акт, С/Ф, Увеличение долга, Уменьшение
долга. Наша: Дата, Документ, Содержание, Дебет, Кредит, Сальдо. Данные для
1С-вида в системе есть (заявка, маршрут из routePoints, водитель, счёт).
Акт сверки — не утверждённая форма, менять можно свободно.

## E. Мелкие несостыковки (проверены по коду)

- `Invoice` (старый) не имеет строк услуг — в счёте PDF строки берутся из
  заявок на лету; расхождение с новым `AccountingDocumentLine`.
- Форма Р-1 у нас альбомная; как печатает 1С — владелец проверяет (открытый
  вопрос из прошлой сессии).
- Регистрация не использует уже написанный eGov-lookup (см. C).
- `getIncomesJournal`/`getExpensesJournal`/`getCounterpartyReport`/…
  без пагинации и без фильтра периода (частично смягчено select'ами).
- Двойная модель идентичности (User.companyId + Affiliation за флагами
  `identity_reads_*` в platformSetting) — переезд не завершён.
- Страницы-гиганты: `orders/[id]` 2428 строк, `users` 2384, `orders` 2190.
  Не срочно; ломать без тестов веба нельзя.

## F. Интерфейс бухгалтерии глазами бухгалтера из 1С

Проверено по коду страниц. Принцип владельца: плотно, тонко, терминология
1С — бухгалтер переходит с 1С и должен узнавать привычное; «лучше 1С» — за
счёт меньшего числа кликов, а не за счёт другого лексикона.

**Счета (`accounting/invoices/page.tsx`).** Плоский список уже есть
(вкладки Исходящие/Входящие, колонки номер/контрагент/даты/рейсы/сумма/
статус). Чего не хватает до удобного журнала документов 1С:
- фильтр по контрагенту — только текстовый поиск; нужен Select контрагента
  + фильтр по периоду (в 1С журнал всегда ограничен периодом);
- нет итоговой строки за выборку (сумма счетов, сумма оплаченных);
- приоритет действий в строке перепутан: «Поделиться ссылкой» — видимая
  кнопка, а печать/PDF — нет. Для бухгалтера первичны Открыть и Печать;
  «поделиться» — в выпадающее меню «⋯»;
- нет «Создать на основании» из строки и «Скопировать счёт».

**Создание счёта (`invoices/create`).** Поток «контрагент → рейсы без
счёта → счёт» правильный (это и есть «ввод на основании»), оставить.
Дополнить обратным входом: из заявки и из строки журнала (T-06).

**Операции (`accounting/operations`).** Единая лента платежей/доходов/
расходов — хорошо (в 1С это разрозненные журналы). Не хватает: период по
умолчанию (сейчас грузится всё), итоги прихода/расхода за период под
таблицей, фильтр по кассе/счёту и контрагенту.

**Отчёты (`reports/page.tsx`, «Конструктор отчётов»).** Три пресета
(P&L по месяцам, по контрагентам, по заявкам). Бухгалтеру с 1С не хватает
печатной шапки (организация, период, дата формирования) и выгрузки каждого
пресета в Excel одной кнопкой (экспорт CSV есть в других местах —
`lib/exportCsv.ts`).

**Терминология.** Выдержать словарь 1С на всех экранах бухгалтерии:
«Проведён» (не «Активен»), «Контрагент», «Организация» (своя),
«Ввод на основании», «Журнал документов». Новые документы показывают
статусы Черновик/Проведён/Отменён. Один раз пройтись по текстам —
дёшево, а узнавание для бухгалтера решающее.

## G. Безопасность — добор к прошлым правкам

- **Публичные ссылки счетов бессрочны и неотзываемы.** `shareToken` —
  uuid (энтропия ок), троттлинг на публичном контроллере есть (20/мин),
  но токен живёт вечно и отозвать его нельзя (проверено: revoke/regenerate
  нет ни в API, ни в UI). Уволенный сотрудник или утёкшая ссылка = вечный
  доступ к счёту с реквизитами.
- **Загрузки файлов** — в порядке: users 5МБ, driver-public 15МБ, печать
  5МБ + проверка MIME (PNG/JPG). Замечание: политика разбросана по
  контроллерам — при добавлении новых загрузок копировать существующий
  паттерн с limits + fileFilter.
- Rate-limit: глобальный 60/мин, вход 5/мин, публичные страницы 10–20/мин —
  без изменений, достаточно.

## H. Разбор по разделам бухгалтерии (сверка с 1С, скриншоты владельца)

Формат: как сейчас → чем мешает → куда ведёт (задача). Эталоны 1С:
карточка «Счет на оплату исходящий» и «журнал Счетов» (см. Журнал, 25.07).

- **Журнал счетов.** Плоский список с переключателем Исходящие|Входящие —
  переключатель СОХРАНИТЬ (требование владельца). Нет фильтров
  Организация/Контрагент/период (в 1С — первая строка журнала), нет
  колонки «Сделка» (заявка-основание), нет печати «Реестр документов».
  → T-15.
- **Карточка счёта.** Сейчас — просмотр старой модели: нет проведения,
  нет «создать на основании», нет выбора организации и банковского счёта.
  В 1С карточка = центр работы: Провести и закрыть / Создать Акт /
  Печать / Создать приход денег; строки с «Документом-основанием»
  (заявка + маршрут/водитель второй строкой). → T-01 (этап б), T-19.
- **Банковские счета/кассы.** Разделы есть (`banks`, `balances`),
  `FinanceAccount` с kind BANK/CASH. Но счёт-документ НЕ привязан к
  банковскому счёту (проверено по схеме Invoice) — в печать всегда идут
  одни реквизиты компании. У кого два счёта в разных банках (как в 1С на
  скриншоте «ЗАПАДНО-УРАЛЬСКИЙ») — печатается не то. → T-19.
- **Оплаты и задолженности.** Статус «Оплачен» у счёта и факт платежа —
  разные сущности, синхронизированы флагами и защитами (M-6), но частичная
  оплата счёта не видна (нет «оплачено X из Y»), распределение платежа по
  счетам не ведётся. → T-07 (расширена).
- **Возвраты.** Операции «возврат платежа» нет вообще (в коде только
  комментарий, что судьба возврата — на бухгалтере). Возврат сейчас можно
  оформить лишь удалением платежа (ломает историю) или встречным платежом
  без связи с исходным. → T-20 (новая).
- **Поступления/расходы/операции.** Единая лента — сильная сторона
  (лучше 1С), нужен период и итоги. → T-17, T-08.
- **ДДС и остатки касс.** Считаются из одного источника
  (`getCashPosition`) — инвариант «ДДС сходится с остатками» уже
  обеспечен; при любых правках этих разделов сохранять общий источник.
- **Взаиморасчёты и акт сверки.** → T-03 (вид 1С + фиксация документом).
- **Счета-фактуры.** Как тип документа отсутствуют (в 1С — «Создать Акт,
  Счет-Фактуру»). Сознательно отложено до ЭСФ-интеграции. → T-13.
- **Реестр заявок (финансовый).** Работает, итоги есть; после T-02
  добавить в строку статус «есть акт / нет акта».

**Сквозная согласованность (требование владельца):** один счёт/платёж/долг
обязан показывать одно и то же в журнале счетов, карточке, взаиморасчётах,
реестре и дашборде. Проверка на это — в КП задач T-01, T-07, T-15.

# Задачи

Приоритет: P1 — нужно до реальной работы клиентов (≈критический/высокий);
P2 — сильно желательно (средний); P3 — потом (низкий). У каждой задачи:

## P1 — довести бухгалтерию до рабочей

- [x] **T-01. Подключить счета нового поколения к вебу.** [критический]
  СДЕЛАНО 25.07 — все три этапа (реестр, карточка, создание).
  Раздел «Счета» = два уровня: общий реестр + карточка документа.
  Перевод с `/invoice` на `/accounting-documents` (PAYMENT_INVOICE).
  Старые счета читаются как раньше (миграцию решает владелец, вопрос № 2).
  Этапы (можно отдельными коммитами/агентами):
  **а) Реестр** (`invoices/page.tsx`): список документов нового типа,
  переключатель Исходящие|Входящие СОХРАНИТЬ, статусы
  Черновик/Проведён/Отменён. Пересекается с T-15 (фильтры/итоги) —
  делать вместе или T-15 сразу после.
  **б) Карточка** (`invoices/[id]/page.tsx`) — СДЕЛАНО 25.07. По образцу
  карточки 1С: шапка (номер, дата, Организация, Банковский счёт,
  Контрагент, вид счёта = направление); строки таблицы: Документ-основание
  (заявка №, вторая строка — маршрут/водитель/авто), услуга, кол-во, цена,
  сумма, ставка НДС; кнопки Провести и закрыть / Провести / Записать /
  Печать; внизу — комментарий, Всего и НДС в т.ч., автор документа.
  Осталось от этапа: кнопки «Создать акт на основании» (ждёт T-06) и
  «Создать поступление денег» (ждёт T-07) — их вешать некуда, пока нет
  цепочки документов и аллокации оплат.
  **в) Создание** (`invoices/create/page.tsx`) — СДЕЛАНО 25.07. Поток
  «контрагент → подобрать по заявкам» сохранён (кнопка «Подобрать по
  заявкам» открывает окно выбора рейсов), добавлено «Добавить услугу»
  вручную из `ServiceCatalogItem`. Номер вручную больше не вводится —
  его выдаёт нумератор. Создаётся черновик, дальше работа в карточке.
  Почему: сейчас счёт — итог одной суммой без строк и жизненного цикла,
  акт печатается из живой заявки и меняется задним числом (см. A).
  Затрагивает: журнал счетов, карточку заявки (цепочка документов),
  взаиморасчёты, PDF.
  КП: счёт со строками проводится и печатается (PDF = эталон 1С, образец
  `scripts/generate-accounting-invoice-sample.ts`); черновик помечен
  водяным знаком; после проведения изменение заявки НЕ меняет счёт;
  сумма счёта в реестре = в карточке = во взаиморасчётах (тест).

- [x] **T-02. Акт выполненных работ — из документа, а не из заявки.**
  СДЕЛАНО 25.07. Журнал актов показывает документы SERVICE_ACT (раньше —
  заявки, и «№ акта» был номером заявки). Кнопка на карточке заявки
  создаёт акт и открывает его карточку, а если акт уже есть — открывает
  существующий, не плодя второй. Страница `act-of-work` осталась
  предпросмотром и подписана как расчёт по текущим данным заявки.

  **Как должно быть.**
  1. `POST /auth/register` создаёт ТОЛЬКО личный профиль — без компании.

  отказа. Существующие компании миграцией помечаются VERIFIED, иначе
  тестовые данные перестанут работать. Эндпоинты: создание компании,
  загрузка документов, отправка на проверку.

  **в) Админка.** Очередь «На проверке», карточка с документами,
