# Аудит LogiCore — 26.07.2026

Полный проход по проекту: код, база, безопасность, казахстанская специфика.
Каждый вывод проверен по коду, с точным местом. Внизу — задачи в формате,
по которому любой ИИ-агент может взять работу без дополнительных вопросов.

Проект: логистическая платформа для РК. Монорепо pnpm, ~80 000 строк:
`apps/api` (NestJS + Prisma + PostgreSQL), `apps/web` (Next.js 14 + Ant Design),
`apps/mobile` (Expo). Прод на Railway, автодеплой с `main` (ждёт зелёный CI).

**Перед любой работой агент обязан прочитать `AGENTS.md` и журнал в конце
`PRODUCT_AUDIT_PLAN.md`.** Правила из них здесь не повторяются, но действуют:
tsc + jest перед коммитом, деньги только Decimal, миграции только через
Prisma Migrate, миграция = бэкап от владельца, ветка живёт один заход.

## Что сделано хорошо (не трогать и не «улучшать»)

1. **Деньги на Decimal.** Весь расчётный контур — `common/utils/money.ts`,
   `accounting-document-calculator.service.ts` — без float. Глобальный
   `DecimalToNumberInterceptor` конвертирует только на выходе. Float в схеме
   остался лишь у координат и веса груза — там ему и место.

2. **Снимки документов.** Счёт/акт хранят `issuerSnapshot`/`recipientSnapshot`,
   договор-заявка и доверенность — версии в `OrderDocument` со снимком.
   Выданный документ не меняется, когда правят карточку. Это правильно, это
   каркас всей бухгалтерии — любая задача обязана его сохранять.

3. **Роли по-настоящему многоорганизационные.** Роль хранится в
   `UserCompanyRelation` (роль в конкретном юрлице), перечитывается из базы
   на каждом запросе (`auth.service.ts` ~строка 200) — увольнение действует
   мгновенно, а не когда протухнет токен. `switchCompany`
   (`company.service.ts:1535`) честно проверяет наличие связи.

4. **Нумерация документов** — отдельные последовательности на
   тип+направление+год, закрыта уникальным индексом
   `@@unique([companyId, type, direction, number])`.

5. **Правило печати:** чужая печать не ставится никогда, своя — только по
   явному флажку (`StampImageService.loadFor`, закреплено тестами).

6. **Базовая гигиена безопасности:** Throttler глобально, JWT_SECRET
   обязателен (падает без него), CORS по списку, ValidationPipe с
   `whitelist + forbidNonWhitelisted`, публичные ссылки новой модели
   документов отзываемы, сканы удостоверений отдаются только через
   защищённый эндпоинт.

7. **370 серверных тестов** на расчётном ядре, многие проверены мутациями
   (тест обязан падать при снятии защиты — см. журнал). CI: build + test +
   проверка словаря интерфейса (`scripts/check-vocabulary.js`).

## Задачи. Приоритет 0 — делать в первую очередь

### A-01. Доступ сотрудников к организациям: дать администратору выбор
**Запрос владельца (26.07):** админ при настройке решает, работает сотрудник
во всех организациях холдинга или только в одной.

**Что сейчас (проверено по коду), поведение противоречивое:**
- Новый сотрудник (`users.service.ts:110-135`) получает связь только с
  ОДНОЙ компанией — той, в которой его создали.
- Но при создании новой организации (`company.service.ts:1460`,
  `addMyCompany`) в неё автоматически копируется ВСЯ офисная команда всех
  существующих организаций — молча, без выбора.
- Итог: доступ «во все» получается только у тех, кто был нанят ДО создания
  организации. Нанятые после — только в одной. Никто этим не управляет.

**Как исправить:**
1. При создании организации (`addMyCompany`) — параметр
   `copyTeam: boolean` в DTO, чекбокс в форме «Добавить организацию»
   (`apps/web/src/app/company/settings/page.tsx`, вкладка организаций):
   «Дать доступ текущей команде». По умолчанию включён (текущее поведение).
2. В карточке сотрудника (`apps/web/src/app/company/users/page.tsx`) —
   блок «Доступ к организациям»: список юрлиц с чекбоксами и ролью в каждом.
   API: `GET/PUT /users/:id/company-access` в `users.controller.ts`,
   работа с `UserCompanyRelation` (создать/удалить связь, поменять role).
   Право менять — только COMPANY_ADMIN той же группы организаций.
3. При найме (`users.service.ts` create) — опциональный список
   `companyIds`; по умолчанию — текущая организация (как сейчас).
   Миграции НЕ нужны: таблица `UserCompanyRelation` уже всё умеет.

**Приёмка:** админ снимает галочку у сотрудника → тот при `switch-company`
получает «нет доступа» немедленно; тест на это. Новая организация с
выключенным `copyTeam` видна только создателю.

### A-02. Вывести из работы старую модель `Invoice` (= T-22 плана)
**Дыра:** `apps/api/src/invoice/public-invoice.controller.ts` отдаёт счёт
по `shareToken` без авторизации, а у модели `Invoice` НЕТ ни отзыва, ни
срока жизни — любая когда-либо отправленная ссылка вечна. Экрана в UI уже
нет, фронт этот API не зовёт.

**Порядок:** снять три оставшихся чтения (`orders.service.ts:689,700`,
`financial-reports.service.ts:1628,1780`, `assistant.service.ts:241`) →
удалить `InvoiceModule` из `app.module.ts` и весь `src/invoice/` → удалить
страницу `apps/web/src/app/shared/invoice/[token]` → последним шагом
миграция DROP таблицы (⚠️ бэкап + отдельное «да» владельца).
**Приёмка:** `GET /public-invoices/:token` → 404; `grep prisma.invoice.` пуст.

### A-03. Часовой пояс: «сегодня» считается по UTC, а Казахстан — UTC+5
**Проверено:** упоминаний `Asia/Almaty` в API нет вообще. Всё, что сравнивает
с «сегодня», живёт по UTC: просрочка счёта (`pending-work.service.ts`,
метод `today()`), dueDate-фильтры журналов, планируемые платежи.
**Следствие:** с 00:00 до 05:00 по Алматы «сегодня» — ещё вчера. Счёт со
сроком «сегодня» ночью уже показан просроченным (или наоборот).
**Как исправить:** один хелпер `common/utils/business-date.ts` —
`todayInKz()`, `startOfDayKz()` (смещение +05:00, у РК с 2024 один пояс без
переводов); заменить все `new Date()`-«сегодня» в сравнениях дат. Поля
`@db.Date` не трогать. **Приёмка:** тест с подменой системного времени на
23:30 UTC: счёт с dueDate «завтра по Алматы» НЕ просрочен.

### A-04. Ставка НДС 16% зашита в трёх местах фронта
С 2026 в РК НДС 16%, и он зашит константой: `OrderEditForm.tsx:335,362`,
`orders/create/page.tsx:1092`. Когда ставка изменится (а она уже менялась с
12 на 16), править придётся поиском по коду.
**Как исправить:** константа `DEFAULT_VAT_RATE = 16` в
`apps/web/src/lib/vocabulary.ts` (или отдельном `lib/tax.ts`) + подстановка
из неё; на сервере — ничего, там ставка приходит с документом и хранится в
снимке (правильно). Опционально: поле «ставка НДС по умолчанию» в
настройках организации рядом с КНП (поля T-10 уже есть — тот же паттерн).
**Приёмка:** `grep -rn "initialValue={16}"` по фронту пуст.

## Приоритет 1 — после нулевого

### A-05. Smoke-тесты веба (= T-23 плана)
Во фронте НОЛЬ тестов при 34 000+ строк. Правка словаря (T-18) задела
20 файлов — проверить можно было только глазами. Chromium в CI-окружении
предустановлен (`/opt/pw-browsers/chromium-1194/chrome-linux/chrome`,
запуск с `executablePath` + `--no-sandbox`; `playwright install` НЕ звать).
Минимум четыре пути: вход → создание заявки → выставление счёта из карточки
рейса → выгрузка отчёта. Селекторы: email-поле
`input[type="email"], input#email`, чекбоксы AntD кликать по `.ant-checkbox`.
Подключить джобой в `.github/workflows/api-tests.yml` (поднять Postgres как
в job `test`, сид `SEED_TEST_DATA=true`).
**Приёмка:** джоба в CI красная, если сломать любой из четырёх путей.
Разблокирует распил страниц-гигантов (T-12: заявки 2190 строк,
пользователи 2384, карточка рейса 2149).

### A-06. Матрица доступов: 9 ролей, проверено 6 файлами тестов
`PermissionsGuard` управляет только тремя ролями (LOGISTICIAN, ACCOUNTANT,
WAREHOUSE_MANAGER — `permissions.guard.ts:22`), остальные проходят мимо
проверки permissions и ограничены только `@Roles`. Систематической проверки
«кто что видит» нет.
**Как сделать:** один спек `apps/api/src/auth/access-matrix.spec.ts` —
таблица «роль × эндпоинт → 200/403» по критичным контроллерам (accounting,
accounting-documents, users, company, reports). Гонять против реальных
guards через `Test.createTestingModule`. Найденные несоответствия НЕ чинить
молча — список владельцу, он решает, что правильно.
**Приёмка:** матрица в тесте читается как документация; падает при
изменении любого декоратора доступа.

### A-07. Автоматический бэкап базы
Сейчас бэкап — только ручная кнопка в Railway перед миграциями. Прода без
реальных данных это терпит, с реальными — нет.
**Как сделать:** cron-сервис в Railway (отдельный сервис в том же проекте):
ежесуточный `pg_dump | gzip` → S3 (S3-модуль в API уже есть, значит и
креды есть), хранить 14 суток, после выгрузки — проверка, что файл
непустой и `pg_restore --list` его читает. Инструкцию положить в
`PRODUCTION_DEPLOY.md`. **Приёмка:** в S3 появляется свежий дамп каждые
сутки; восстановление на локальной базе проходит (описать команду там же).

### A-08. Входящие/исходящие документы между компаниями платформы
Продуктовый разрыв (вопрос владельца от 26.07, решение согласовано, не
реализовано): если обе компании на платформе, документ от А к Б сам не
приходит — Б заводит руками. План записан в `PRODUCT_AUDIT_PLAN.md`, раздел
«Открытый вопрос: входящие и исходящие»: один документ + доступ на чтение
получателю, действие «Отправить контрагенту», сопоставление по БИН,
у получателя только принять/отклонить. Крупная задача, дробить на API/UI.

### A-10. Тесты на 17 модулей без единого теста
Из 34 модулей API без тестов 17. Приоритет по риску: `billing` (деньги
подписок), `users` (доступы), `partners`, `external-companies`,

`auth/dto/*.ts` — `@MinLength(6)`. Для системы с бухгалтерией слабо.
Поднять до 8 на регистрацию и смену (существующие пароли не трогать).

### A-12. Косметика списка организаций
`getMyCompanies` (`company.service.ts:1382-1391)`: если активной компании
нет в связях, она дорисовывается с ролью `user.role || 'COMPANY_ADMIN'` —
список может показать организацию и роль, которых у человека фактически
нет. На доступ не влияет (switchCompany проверяет честно), но врёт в UI.

### A-13. 357 `any` в API
`AGENTS.md` запрещает `any` в новом коде — правило соблюдается, но старые
лежат. Чистить попутно: трогаешь файл — типизируешь его `any`.

### A-14. Решить судьбу двух вещей (решает владелец, не агент)
- **Казахский язык:** i18n отсутствует, интерфейс только русский. Для
  рынка РК может понадобиться казахская версия — это большая работа,
  начинать только по явному решению.
- **ИИ-ассистент шлёт данные в DeepSeek** (`assistant.service.ts:184`,
  api.deepseek.com): фрагменты бизнес-данных уходят третьей стороне.
  Либо осознанно оставить и написать это в интерфейсе, либо выключить.
- **Мобильное приложение** давно не менялось — жив ли план по нему.
- **Публичный репозиторий** на GitHub Free: код виден всем (секретов в нём
  нет — проверено), защита ветки на приватном требует платного тарифа.

## Про нагрузку (вопрос владельца)

Нагрузочного тестирования не было ни разу, honest answer — предел неизвестен.
Ориентиры по устройству: один инстанс API на Railway, Postgres там же,
Redis для сессий. Для команды в десятки человек запаса хватит с большим
запасом; узкие места при росте — журналы без `take` и отчёты, считающие
по всей истории (`getCounterpartyReport` — сальдо за всё время, это
осознанно). Отдельная задача по замерам имеет смысл после появления
реальных данных: мерить пустую базу бессмысленно.
